Engineering case study

Five repos. One index.
No copy-pasted files.

A repo-agnostic RAG server over the Model Context Protocol: point it at any Java codebase, it indexes the code with a real AST parser, and an MCP client gets five read-only tools to search and browse it — never a server-side LLM call, never a hard-coded assumption about how any one repo is laid out.

The proof

real stdio JSON-RPC, captured stdout

The MCP stdio transport reserves stdout exclusively for JSON-RPC messages. The first live test — piping a real initialize → tools/list → tools/call sequence into a running process and capturing stdout — caught a real bug before any actual client had the chance to.

How it works

one jar, two entry points

The same jar serves both jobs. Run with --index <path> <name>, the CommandLineRunner does a one-shot walk-chunk-embed-store and exits; run with no arguments, that runner returns immediately and the app starts as an MCP server instead.

Three decisions, not defaults

Chunk by file type, not by convention

Hard-coding each portfolio repo's folder layout would break the moment a new repo had a different shape — and defeat the point of building one tool for all of them. Each file is handed to whichever chunker claims its extension; Java is parsed with a real AST, not brace-counting, so nested classes and braces in strings don't break it.

JavaClassChunker.java

Retrieval only, never the model

It would have been easy to make a tool synthesize prose server-side. That's the wrong shape for MCP — the client already has a model in the loop. Every tool returns raw matched chunks and scores; the calling LLM decides what to do with them.

RagTools.java

stdout is reserved — verify, don't assume

The framework doesn't know stdout is sacred under stdio transport by default. A live wire-level test with real captured output caught Spring Boot's own banner and logs leaking into the JSON-RPC stream, before any real client had to find out the hard way.

The five tools

ToolWhat it does
list_indexed_reposEvery indexed repo with file and chunk counts — the discovery entry point.
search_codeSemantic search over indexed chunks, optionally scoped to one repo.
get_fileEvery indexed chunk for one file, by repo + path.
list_structuresEvery indexed symbol — class, interface, enum, record, or markdown heading — optionally scoped to one repo.
explain_conceptExact symbol match plus related semantic search results for a named concept — evidence for the caller to build an explanation from.
